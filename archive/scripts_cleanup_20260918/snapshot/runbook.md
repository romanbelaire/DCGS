# DCGS experiment runbook

This checkout contains the DCGS source and selected critic checkpoints. It does
not contain the base language models, cached datasets, original experiment JSON
files, or an exact dependency lock. This runbook establishes a practical
environment for CARES and WildJailbreak smoke tests.

## 1. Start on a GPU compute node

Do not run the experiments on the login node. `src/main.py` enforces these GPU
memory minimums:

- Evaluation: at least 32 GB VRAM
- Training: at least 40 GB VRAM

SCIS uses Slurm GPU GRES. Always request a **typed** GPU; an untyped
`--gres=gpu:1` request can select an 11, 16, or 24 GB device that this program
will reject. The GRES names can be checked with:

```bash
sinfo -N -o '%N|%P|%G|%m|%c|%t'
```

This account is associated with Slurm account `pradeepresearch` and the
`researchshort` and `researchlong` partitions. The following request was
validated with `sbatch --test-only`; it selects a 48 GB L40 and is suitable for
both evaluation and heads-only training:

```bash
srun --account=pradeepresearch --partition=researchshort --gres=gpu:l40:1 \
  --mem=64G --cpus-per-task=8 --time=02:00:00 --pty bash
```

Use `researchlong` instead when the requested wall time exceeds the short-queue
policy. Do not hard-code the currently matched node (`lagoon`); choosing the
`l40` GPU type lets Slurm place the job on any eligible node. If your account or
partition associations change, select one of the compatible typed GRES values
below.

| GRES type | Per-GPU memory | DCGS use |
|---|---:|---|
| `a100` | 40 GB | Evaluation and heads-only training |
| `a40`, `l40`, `l40s` | 48 GB | Evaluation and heads-only training |
| `h100` | 80 GB | Evaluation and training |
| `h100_nvl`, `rtx_pro_6000_blackwell_max` | 96 GB | Evaluation and training |
| `h200` | 141 GB | Evaluation and training |

The supplied inventory also lists 32 GB V100, 46 GB Quadro RTX 8000, and
smaller GPUs. They are not recommended for this configuration: V100/Turing-era
devices do not natively support BF16, while all 11--24 GB devices fail the
program's memory gate. The static inventory is at
`../Setup/SCIS GPU Cluster Compute Nodes - Servre Information.csv` relative to
the `RL-Defense` directory. Confirm current scheduling state with `sinfo`, since
the CSV describes hardware rather than live allocation state.

See the SCIS [Select GPUs documentation](https://violet.scis.dev/docs/Advanced%20settings/selectGPUs)
for the cluster's GPU-selection policy and additional allocation forms.

After allocation, verify that Slurm exposed exactly the requested GPU:

```bash
hostname
echo "$CUDA_VISIBLE_DEVICES"
nvidia-smi
```

After activating the Python environment in the next section, also verify that
PyTorch can use the allocated device. Do not start an experiment unless
`torch.cuda.is_available()` prints `True` and `nvidia-smi` reports enough memory
for the selected mode.

## 2. Create the Python environment

Python 3.10 or 3.11 is recommended. From the `DCGS` directory:

```bash
module load Python/3.11.11-GCCcore-13.3.0
python -m venv .venv
source .venv/bin/activate
python -m pip install uv
```

The final command uses pip only to bootstrap `uv` inside the new environment.
All project dependencies are then managed through `uv`.

This cluster's virtual environment depends on shared libraries supplied by the
Python module. In every new shell, load the same module before activation:

```bash
module load Python/3.11.11-GCCcore-13.3.0
source .venv/bin/activate
```

Install the repository dependencies, including the CUDA-enabled PyTorch wheel:

```bash
uv pip install -r requirements.txt
```

If the cluster later requires a different PyTorch/CUDA build, install that build
with `uv pip install` using the index URL generated by the official PyTorch
selector, then rerun the requirements command. Verify the environment and GPU:

```bash
uv pip check
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'NO GPU')"
```

When `uv pip install -r requirements.txt` reports `Checked 15 packages`, all
top-level requirements are already satisfied and no reinstall is necessary.

## 3. Configure credentials

Edit `.env` and fill the values needed by the experiment. Never commit this
file. Load it into the current shell with:

```bash
set -a
source .env
set +a
mkdir -p "$XDG_CACHE_HOME" "$HF_HOME" "$PIP_CACHE_DIR" "$UV_CACHE_DIR" "$MPLCONFIGDIR"
```

For the API-backed smoke configuration below, `OPENAI_API_KEY` is required.
Set `OPENAI_BASE_URL` only when using an OpenAI-compatible gateway; leave its
line commented out for direct OpenAI access rather than exporting an empty
value. `HF_TOKEN`
is recommended for model and dataset downloads and is required for gated Hugging
Face assets.

Check that variables are populated without printing the secrets:

```bash
test -n "$OPENAI_API_KEY" && echo "OpenAI key: set" || echo "OpenAI key: missing"
test -n "$HF_TOKEN" && echo "Hugging Face token: set" || echo "Hugging Face token: missing"
```

You can also authenticate the Hugging Face CLI:

```bash
hf auth login
```

Before starting an API-backed experiment, test the endpoint and key without
submitting a paid generation request:

```bash
python scripts/test_openai_connection.py
```

The script loads `.env` automatically, does not print the key, disables retries,
and distinguishes authentication failures from DNS/TLS/network failures. A
successful connection may still warn when the configured model is not returned
by the endpoint's Models API.

If it reports a proxy URL with no protocol, temporarily remove inherited proxy
settings and retry direct OpenAI access:

```bash
unset HTTP_PROXY HTTPS_PROXY ALL_PROXY http_proxy https_proxy all_proxy
python scripts/test_openai_connection.py
```

This changes only the current shell. If direct access then times out, restore a
valid SCIS proxy configuration whose URL begins with `http://` or `https://`.
If the same proxy error remains after unsetting those variables, bypass all
HTTPX environment discovery for diagnosis:

```bash
python scripts/test_openai_connection.py --ignore-environment-proxy
```

## 4. Verify the critic checkpoints

```bash
ls -lh outputs/cares_hierarchical_regret_critic/hierarchical_regret_critic/checkpoints/value_function_latest.pt
ls -lh outputs/wildjailbreak_hierarchical_regret_critic/hierarchical_regret_critic/checkpoints/value_function_final.pt
```

Expected sizes:

- CARES latest: 503,587,623 bytes (about 481 MiB)
- WildJailbreak final: 251,806,417 bytes (about 240 MiB)

The critic checkpoint does not contain the base actor. The first run downloads
`HuggingFaceH4/zephyr-7b-beta` and the selected dataset from Hugging Face.

  "use_hierarchical_agent": true,

  "critic_only_training": true,

  "use_gpt_for_patient": true,

(`critic_lora_r=0`), and the regret critic enabled.

## 6. Run the smoke evaluation

From `DCGS`, with the virtual environment and `.env` loaded:

```bash
export LLM_CONTEXT_EVAL_MODE=1
python -m src.main cares_smoke.json outputs/cares_smoke
```

Evaluation mode disables gradient-based value updates and prevents the loaded
checkpoint from being overwritten. Watch the first run for Hugging Face access,
CUDA out-of-memory, API authentication, or checkpoint shape errors.

Inspect the output afterward:

```bash
find outputs/cares_smoke -maxdepth 2 -type f -print
```

## 7. Scale up carefully

Once the two-example smoke test completes:

1. Preserve the working JSON as an immutable smoke configuration.
2. Copy it to a separately named pilot configuration.
3. Increase `max_dialogues`, `evaluation_sample_size`, and `max_turns` gradually.
4. Record the GPU type, package versions, model revisions, dataset revisions,
   random seeds, API model identifiers, and exact checkpoint for every run.
5. Use a new output directory for every configuration and seed.

To capture the installed Python environment:

```bash
uv pip freeze > outputs/cares_smoke/environment-freeze.txt
```

## 8. Generate a SafeDialBench no-defense baseline

SafeDialBench uses a different evaluation protocol from CARES. Its local
baseline runner generates an answer for every user turn against the dataset's
**gold assistant history**. The generated answer is saved but is not fed into
the following turn. This matches the benchmark's counterfactual turn protocol.

First confirm that the pinned English dataset is present and select a balanced
12-dialogue smoke set (two dialogues from each safety dimension), without
loading the model:

```bash
python scripts/run_safedial_baseline.py --per-task 2 --validate-only
```

The expected IDs are `3,4,1,2,40,41,102,103,25,26,49,50`. Run the plain
Zephyr baseline on the allocated GPU:

```bash
python scripts/run_safedial_baseline.py \
  --per-task 2 \
  --output-dir outputs/safedial_baseline/zephyr_7b_beta_smoke
```

This is a generation-only run: it does not load a DCGS value function and does
not call an API judge. It creates:

- `run_config.json`: dataset hash, selected IDs, model, seed, and decoding setup
- `answers.jsonl`: one record per dialogue in the format expected by the
  SafeDialBench judge
- `turns.jsonl`: one auditable record per choice and turn, including gold prompt
  history, generated and reference responses, tokens, latency, seed, and errors

The runner saves each completed dialogue and automatically skips it when the
same command is resumed. Use `--retry-errors` to regenerate only dialogues whose
latest answer contains an error. A changed selection or decoding configuration
must use a new output directory, which prevents unlike runs from being mixed.

After manually checking the 12-dialogue output, generate the complete English
baseline by omitting the selection flag:

```bash
python scripts/run_safedial_baseline.py \
  --output-dir outputs/safedial_baseline/zephyr_7b_beta_full
```

Judging is deliberately a separate step. Do not treat generation completion as
a safety score; the official SafeDialBench judge still needs to be run on
`answers.jsonl` after its judge integration is validated.

## 9. Generate SafeDialBench answers with DCGS

The standalone DCGS runner preserves SafeDialBench's counterfactual protocol:
every generated response sees the benchmark's gold assistant history, and a
generated response is never fed into a later turn. At each turn it reconstructs
the DCGS state, generates nominal and adversarial high-level candidates, scores
them with the Q/regret critic, samples an instruction with the DCGS policy, and
generates the low-level response.

The default `safedial_dcgs.json` uses the WildJailbreak-trained regret critic,
which is the available general-safety critic and is a closer domain match than
the clinical CARES critic. Validate the full dataset, balanced smoke selection,
configuration, and checkpoint architecture without loading the model:

```bash
python scripts/run_safedial_dcgs.py --per-task 2 --validate-only
```

Before a full run, use a separate GPU allocation for a one-dialogue smoke test:

```bash
python scripts/run_safedial_dcgs.py \
  --ids 1 \
  --output-dir outputs/safedial_dcgs/zephyr_7b_beta_wildjailbreak_critic_smoke
```

The runner is resumable by dialogue and creates the same judge-compatible
`answers.jsonl` as the baseline. Its `turns.jsonl` additionally records the gold
DCGS state, candidate beliefs, Q values, regret values, selection probabilities,
selected belief, and raw high-level outputs. Use `--retry-errors` to retry only
dialogues containing an error. Do not reuse a baseline output directory.

After a successful smoke test, the full generation command is:

```bash
python scripts/run_safedial_dcgs.py \
  --output-dir outputs/safedial_dcgs/zephyr_7b_beta_wildjailbreak_critic_full
```

Run the full command through a dedicated `researchlong` Slurm batch script; it
is substantially more expensive per turn than the no-defense baseline because
it performs high-level candidate generation and critic scoring before response
generation.

## 10. Judge the SafeDialBench outputs

The standalone judge uses the six task-specific rubrics pinned in the cloned
SafeDialBench repository and accepts either baseline or DCGS `answers.jsonl`.
For each turn it supplies gold prior assistant turns as context and evaluates the generated current response. Its dialogue-level
Identification, Handling, and Consistency scores are the minimum values observed
across the judged turns, matching the benchmark logic.

Validate the smoke answers and see the number of paid API requests first:

```bash
python scripts/judge_safedial.py --dry-run
```

The 12-dialogue smoke run requires 62 judge requests. Confirm API connectivity,
then run the judge:

```bash
python scripts/test_openai_connection.py
python scripts/judge_safedial.py \
  --answers outputs/safedial_baseline/zephyr_7b_beta_smoke/answers.jsonl \
  --output-dir outputs/safedial_baseline/zephyr_7b_beta_smoke/judgments_gpt-4o-mini \
  --judge-model gpt-4o-mini \
  --parallel 4
```

The default temperature is `0.7` and the default maximum is 2,048 judge output
tokens, matching the bundled OpenAI judge. The output directory contains:

- `judge_config.json`: immutable input hashes and judge configuration
- `judgments.jsonl`: raw per-turn responses, parsed scores, token usage, latency,
  attempts, and explicit errors
- `dialogue_scores.jsonl`: per-dialogue minimum scores in a format compatible
  with the benchmark's downstream reports
- `aggregate.json`: completion status plus overall, task, and attack-method means

The judge saves successful calls immediately. Rerunning the identical command
skips those calls and retries only missing or failed judgments. Never interpret
an incomplete aggregate as a final result; require `"complete": true` in
`aggregate.json`.

## Optional local guard setup

The smoke config uses API-based patient simulation and judging to reduce GPU
memory use. To use a local safety model instead, disable the API judge and set,
for example:

```json
{
  "use_gpt_for_judge": false,
  "reward_model_type": "llamaguard",
  "reward_model_name": "meta-llama/Llama-Guard-3-8B"
}
```

This requires accepted Hugging Face access to the gated model and substantially
more GPU memory. Local patient simulation may also load a separate user model.

## Known reproducibility limitation

The repository snapshot does not include the original requirements lock or
experiment configuration files. `requirements.txt` therefore defines supported
version ranges rather than claiming the exact environment used to train the
released checkpoints. Before a full paper reproduction, recover the original
lockfile/configs or freeze and archive a validated replacement environment.
